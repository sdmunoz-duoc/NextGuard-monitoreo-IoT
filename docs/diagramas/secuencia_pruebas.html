Secuencia de las pruebas

Cinco escenarios entre el ESP32, la API, PostgreSQL e InfluxDB (más el verificador): qué mensajes se cruzan y qué respuesta se espera.

  • A y B muestran por qué (sensor, seq) es la clave de idempotencia: PostgreSQL la garantiza con una clave primaria y el reintento recibe 200 sin escribir otra vez en InfluxDB.
  • En C la API responde sin consultar InfluxDB; con 401/403 el ESP32 no descarta la muestra (es un problema de configuración) y con 422 sí (el dato es inválido).
  • En D, si InfluxDB falla se borra la marca de seq para que el reintento no se tome por duplicado; /health distingue qué base cayó (503 con postgres o influxdb en «sin conexión»).
  • InfluxDB 2.x tarda unas décimas de segundo en hacer visible una escritura: las verificaciones consultan con reintentos hasta 10 s.
